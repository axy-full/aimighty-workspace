# Workspace two-step sign-in policy

The workspace owner can require authenticator enrollment from People → Workspace sign-in policy. Existing workspaces default to optional; deployment does not enable the policy for any customer. The owner must enroll first and supply their current password and a fresh authenticator or recovery code for either policy change.

When required, unenrolled members retain access to their account-security page, workspace selection and account-level onboarding. Studio, Gen, private media, project data, usage and other tenant routes refuse reads and writes with `428 MFA_REQUIRED`. Studio, movie, billing and the application pages redirect to enrollment before serializing workspace data. The identity endpoint returns only minimal account/workspace information while blocked, without credits, rates, model defaults or production setup. Existing API tokens are refused until their account has enrolled; token standing is checked against the authoritative account and membership, even when a tenant mirror is stale.

The account's existing MFA implementation verifies an authenticator before enabling it, replaces earlier sessions and supports single-use recovery codes. The enrollment page keeps recovery codes visible until acknowledged and then offers a full navigation back to Studio. An already-open Studio tab offers security setup in a separate tab when its identity refresh observes the requirement, preserving unsaved edits. This policy restricts future requests; it cannot retract assets already downloaded or memory already held in a previously authorized browser. Previously admitted background jobs and separately issued review-link capabilities retain their existing authorization rules.

Account MFA cannot be disabled while any active membership requires it. Ownership, membership, fresh factor use, policy mutation and its append-only security event are checked and committed in the same platform transaction. A concurrent factor disablement cannot leave an unenrolled owner behind a required policy. The last recovery code cannot be consumed to change policy without first preparing and activating replacements. Lost policy responses are followed by a read of the saved policy; the client does not automatically replay a factor-consuming request.

Verification covers owner/admin distinctions, changed ownership, revoked sessions, stale captured scopes, recovery-code replay, audit-write rollback, last-code protection, simultaneous policy/factor changes, cross-workspace requirements and existing API tokens. The browser flow runs at 360×640, 390×844, 844×390, 1440×900 and 1920×1080 against local mock accounts with real authenticator verification and zero emailed invitations. It checks existing member denial, minimal identity responses, switching to another workspace, all page guards, enrollment, code acknowledgment, restored API access and a lost policy response.

This is an enrollment policy with TOTP and recovery codes. SSO, passkeys, SCIM, organization-managed recovery and independent penetration testing remain separate work.
