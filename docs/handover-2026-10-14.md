## 3. How the work flows (step by step)

1. **The owner decides.** The lead records each decision verbatim in `docs/redesign-plan.md` (on `redesign/integration`) and logs it in `docs/redesign-progress.md`, timestamped in IST (`TZ=Asia/Kolkata date +%H:%M`). The lead pushes the log often.
2. **The lead briefs a lane.** Small PR, one concern, the owner's words quoted, the rules restated (worktree, heavy.sh, no CI, no guard edits, localhost). Lanes are Sonnet agents spawned with the Agent tool and resumed with SendMessage. **Agent IDs belong to one session; a new account must spawn new agents** (section 9).
3. **The lane builds** in `~/wt/<name>`, branched from `origin/release/1`, and runs only its touched specs through heavy.sh. Browser specs use a slot (`slot.sh acquire`), then a mock server (`mock-server.py start`), then playwright with `-c playwright.workbench.config.ts --project=workbench-1440x900 --workers=1`, then stop and release. It pushes and opens a PR to `release/1`, titled "NEEDS AKSHAY · …" where it applies, and says MIGRATION in the title when it adds a column or table.
4. **Lane pushes trigger CI automatically.** The lead cancels those runs: `gh run list --branch <b>` then `gh run cancel <id>`.
5. **Review.**
   - Privacy, money or sign-in: an Opus reviewer, read-only, using its own temp worktree. It answers APPROVE or a numbered list, and the lane fixes and pushes. Repeat until APPROVE.
   - Other screen work: the lead reviews the diff and the screenshots.
6. **CI.** The lead runs CI with `freshrun.sh` (close and reopen the PR, confirm the run's merge base equals the current release/1 head), at most 2 PRs at once. The full run is 25 jobs (24 succeed, 1 skipped when green).
7. **Merge.** The lead runs `gh pr merge <n> --merge --match-head-commit <FULL 40-char sha>`. A short sha fails. Release/1's own full run must then be green.
8. **Deploy PR.**
   - Push `deploy/<date>` at a green release/1 commit (fast-forward), and open a PR to main titled "(not merged)".
   - In the body: contents with commits, migrations (what each changes, and whether it is safe to roll back), and env names only.
   - The owner backs up if there are migrations, merges and deploys in Coolify.
9. **Post-deploy.** The lead waits until `https://particl.si/api/health` reports the new short commit on every hit, then runs read-only checks: health, pages, Google start redirect, and anonymous 401s on private APIs. The signed-in checks are the owner's.

**Gotchas learned the hard way**
- `gh pr merge --match-head-commit` needs the full sha.
- `freshrun.sh` can pick up an older run if the close/reopen didn't create one; check the run id and base.
- Lane pushes create CI runs constantly; cancel them, or you exceed 2 PRs in CI.
- Turbopack won't run from a symlinked worktree, so lanes use `next dev --webpack`. CI uses Turbopack, so rare differences are possible.
- Webpack dev drops idle routes and recompiles them in 10–15 s, which can time out `/api/health` in local runs. #682 added a warm-up global setup (`tests/workbench.warmup.ts`).
- The permission classifier blocks test edits that look like removing a safety test, even when the owner approved them.
  - The five-minute swap on #665 was refused twice for lanes ("Security Test Removal").
  - It went through in the lead's own window, where the owner could approve the prompt.
  - Never route around a refusal.
- `slot.sh` refuses below 40% free memory. A lane once started a server anyway (a slip); that is not allowed.
- The droplet's 0.0.0.0 listeners on 8080, 8000, 6001 and 6002, and the `next-server` processes run by user 1001, are PRODUCTION. Don't touch them.

## 8. Read-only answer: what does every take record? (the owner's question 5)

Read from code on release/1 `890d559c`. No database was opened and nothing was queried.

**A take** is a row in `generations`, in **each workspace's own database** (`lib/db.ts:107` plus the added columns from about line 1040).

| What the owner asked | Where | Columns |
|---|---|---|
| **Model** | `generations` | `model` (the engine model id), `provider` (who made it), `billed_to` (whose balance paid the vendor), `kind`, `task` |
| **Settings** | `generations` | `prompt`, `params` (JSON: aspect, duration, resolution, references, seed, mapping, `madeIn` and so on), `title`, `source_gen_id`, `shot_id`, `version`, `project_id`, `duration_s` / `duration_ms` |
| **Prompt enhancement** | `generations` | `refine_model`, `refine_in_tokens`, `refine_out_tokens`, `refine_cost_usd`, `refine_ledger` |
| **Engine cost (vendor $)** | `generations` | `cost_usd`, `total_tokens`, `rate_usd_per_m` |
| | `meter_events` (**platform database**, one row keyed by the take's id; `lib/platform.ts:155`) | `engine_cost_usd`, `engine`, `model`, `status`, `paid_by_platform`, `credit_usd`, `credit_margin`, `overrun_usd`, `provider_outcome`, `duration_ms`, `created_by` |
| **Billed credits** | `meter_events` | `billed_credits`, plus `meter_credit_receipts` (credits counted per event) |
| **Approved / rejected** | `generations` | `review_state` (`''` unreviewed / `picked` / `approved` / `changes` = sent back), `picked_by`, `picked_at`, `approved_by`, `approved_at`, `review_by`, `reviewed_at` |
| | `notes` (workspace database, `gen_id`) | **The reject reason** is saved as a note on the take (TakeCard: "Reject needs a reason … saves it as a note on the take"). |
| **Who / when / outcome** | `generations` | `created_by`, `token_id`, `created_at`, `updated_at`, `settled_at`, `status`, `error`, `provider_outcome`, `attempts`, `deleted`, timing columns (`queue_ms`, `refine_ms`, `submit_ms`, `engine_ms`, `notice_ms`, `store_ms`), `bytes`, `stored_url` |

**What's missing or weak (findings, no changes made):**
1. **Billed credits are not on the take's own row.** They live only in the platform database's `meter_events`, joined by id. The workspace export already joins them, but anything reading the workspace database alone can't see what a take cost the customer.
2. **"Rejected" isn't its own state.** It is `review_state = 'changes'`, and the reason is free text in `notes`, not a structured column. The reject chips ("Off the brief", "Wrong framing" and so on) aren't stored as a category. A rejected-then-replaced take and a "changes requested" take look the same.
3. **`picked_by`, `approved_by` and `review_by` store the person's display NAME, not their user id** (`app/api/jobs/[id]/route.ts` writes `got.user.name`). If someone renames themselves or leaves, the trail can't be tied back reliably.
4. **No snapshot of the approved price per take.** The quote, approval and fingerprint live in `generation_requests` and the reservation tables, but `generations` doesn't keep the quoted credits or the approval that covered it. Linking them goes through the request key.
5. **Settings are a free-form JSON `params`** with no schema version, so older takes may lack fields newer code expects.
6. **Two databases.** The engine cost is in both `generations.cost_usd` (workspace) and `meter_events.engine_cost_usd` (platform). Which one is final for a given take depends on the reconcile path; there's no single canonical column.

Any change here (for example adding `billed_credits` or a structured `reject_reason` to `generations`) is a migration and NEEDS AKSHAY.
